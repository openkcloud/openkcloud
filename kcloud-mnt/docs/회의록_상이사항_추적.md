### #1 클라우드 자원 메뉴 구조 통합 (2026-10-02)

**회의록/목업 결정 (이전 상태)**
- mockup-v2(v2.1) CLAUDE.md: `// 관리자 전용 구성 섹션 — 260702 회의록 2.2 관리자 메뉴안 "네트워크·볼륨·서비스 구성"`
- 구현: 관리자 화면에서 IaaS/PaaS 하위를 **간소화**하고(프로젝트·가상서버·이미지 / 클러스터·워크로드·설정), 네트워크·라우터·보안그룹·키페어·볼륨·서비스·SC/PV를 **"네트워크·볼륨·서비스 구성"이라는 별도 섹션**으로 뺐다.

**변경 내용 (현재)**
- "네트워크·볼륨·서비스 구성" 섹션 **제거**. 단일 **"클라우드 자원"** 섹션으로 통합.
- **관리자 = IaaS/PaaS 전체 자원**(프로젝트·가상서버·네트워크·라우터·보안그룹·키페어·볼륨·이미지 / 클러스터·워크로드·서비스·스토리지·설정).
- **사용자 = 부분집합**(라우터·이미지플레이버 제외). 관리자 ⊇ 사용자.
- 반영: `MNT-APP/src/lib/nav.ts`(프론트 폴백) + `MNT-CORE/db/seed.sql`(DB 원천, mnu_menu·mnu_role_menu).

**변경 근거**
- 기존 구조는 **역전 모순**: "전반 관리"를 해야 할 **관리자가 사용자보다 IaaS 하위 메뉴를 적게** 보게 됨(관리자 3개 vs 사용자 7개). "관리자=전체, 사용자=일부"라는 대원칙과 배치됨.
- 같은 경로(`/iaas/networks` 등)가 두 메뉴 행으로 중복 존재하는 구조적 중복도 해소.

**실질 결정과의 관계 (중요)**
- HANDOFF §4의 **실질 결정은 "생성 주체 구분"**(네트워크: 관리자 공용/사용자 내부, 볼륨: 사용자 자율 CRUD 등)이며, 이는 **그대로 보존**된다 → 생성 권한 차이는 메뉴 배치가 아니라 **각 화면의 액션(버튼) 수준**에서 처리.
- 즉 이번 변경은 **"권한 결정"이 아니라 "메뉴 배치"만** 바꾼 것이라 등급 🟡.

**영향 / 리스크**
- 검수자가 260702 회의록 2.2의 "네트워크·볼륨·서비스 구성" 메뉴안을 **필수 산출물**로 본다면 지적 가능.
- 대응: 생성 주체 구분은 유지했음을 설명. 필요 시 회의록 2.2 원문이 "별도 섹션 명시"인지 "관리자가 그 기능을 가진다"인지 확인 후 조정.

**되돌리는 법**
- `nav.ts`에서 `SECTION_CLOUD`를 `SECTION_CLOUD_USER`/`SECTION_CLOUD_ADMIN`/`SECTION_CONFIG_ADMIN` 3분할로 복원 + seed.sql의 `sec.netcfg`/`netcfg.*` 행·매핑 복원.

### #2 키페어 생성 주체 — 관리자(회의록) vs 사용자 self-service(구현) (2026-10-07)

**회의록 결정**
- 2026-10 회의: "키페어, 라우터, Floating IP, 보안그룹 **생성 기능은 관리자 권한** 기능으로 추가하기로 함."

**변경 내용 (현재 구현)**
- 키페어는 **사용자 self-service**로 유지. 브라우저(WebCrypto)에서 RSA 3072 생성 → **개인키는 브라우저에만**(다운로드), **공개키만 포털 DB(`iam_ssh_key`)** 저장. 소유자=사용자.
- 라우터·FIP·보안그룹은 회의록대로 **관리자 전용**(사용자 화면에서 쓰기 버튼 숨김).

**변경 근거**
- 보안상 **개인키는 사용자만 보유**해야 하므로, 관리자가 키페어를 생성하면 개인키 전달 경로가 생겨 위험. 공용 클라우드도 키페어는 사용자 self-service가 표준.
- 사용자 확인(2026-10-07): "키페어는 사용자가 하는 게 맞다."

**영향 / 리스크**
- 검수 시 회의록 "키페어=관리자"와 불일치 지적 가능 → 위 보안 근거로 설명, 다음 회의에서 확정.

**되돌리는 법**
- 키페어 메뉴를 관리자 역할로 이동(`seed.sql` mnu_role_menu) + 생성 UI를 관리자 화면으로. 단 개인키 전달 방식 재설계 필요.

### #3 사용자 화면 볼륨·FIP 쓰기 제한 (2026-10-07)

**이전 상태 / 결정**
- HANDOFF §4: "볼륨 사용자 자율 CRUD". 볼륨 화면에 사용자도 생성·확장·삭제·스냅샷 가능.
- FIP 생성 주체는 명시 안 됨(네트워크 상세의 FIP 탭에서 누구나 확보·연결·반납 가능했음).

**변경 내용 (현재)**
- 회의록(2026-10)에 맞춰:
  - **볼륨**: `output/volumes/page.tsx` — 사용자 화면에서 **생성 버튼·확장·삭제·스냅샷 생성/삭제 숨김(조회 전용)**. 볼륨은 자원 신청에서 **flavor 선택 시 자동 생성**되는 흐름(동료 담당)과 일치.
  - **FIP**: `networks/page.tsx` FipTab — **확보·연결·연결해제·반납을 관리자 전용**, 사용자는 조회·IP 복사만.
  - 네트워크 상세의 **서브넷 추가·네트워크 삭제·SG 규칙 편집**도 관리자 전용(네트워크 생성=관리자 원칙과 일치).

**변경 근거**
- 회의록: "네트워크 생성=관리자", "볼륨은 flavor 선택 시 자동 생성", "키페어·라우터·FIP·보안그룹 생성=관리자". → 사용자는 **관리자가 제공한 자원을 선택/조회**하는 모델.
- 자원 신청 워크플로우는 **다른 동료가 담당**하므로, 본 포털(IaaS 조회·운영)에서는 사용자 생성 경로를 열지 않는다.

**영향 / 리스크**
- 권한 게이팅은 현재 **프론트 표시 수준**(mock 인증). 실제 강제는 Keycloak 연동 후.

**되돌리는 법**
- 각 화면의 `canWrite`/`isAdmin` 가드를 제거하면 복원.
