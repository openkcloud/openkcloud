# 테스트배드 프론트엔드 적용 과정 (M1)

> ETRI 관리망 테스트배드(Genestack, OpenStack-on-K8s)에 notebook 프론트엔드를
> **프로세스 실행 + Istio ingress 노출** 방식으로 배포한 전체 절차.
> 레지스트리/CI 파이프라인이 없고, controller 노드에 sudo 권한이 없는 제약 하에서 진행.
>
> - 작성일: 2026-09-28
> - 대상 브랜치: `feature/real-notebook-api` (프론트), `feature/cmp-backend` (백엔드, M3에서 사용)
> - 결과: **M1 완료** — 맥북 브라우저에서 `https://notebook.kcloud.cluster.local:25443` 목업 포털 접속 성공

---

## 1. 개요

### 목표
notebook 기능(프론트 + 백엔드)을 테스트배드에 올려 실제 배포 환경에서 검증한다.
마일스톤을 나눠 진행:

| 마일스톤 | 내용 | 상태 |
|---|---|---|
| **M1** | 프론트엔드(목업 모드)를 프로세스로 띄우고 Istio ingress로 외부 노출 | ✅ 완료 |
| **M2** | Magnum으로 테스트용 서비스 클러스터 생성 + Kubeflow 설치 | ⬜ |
| **M3** | 백엔드(uvicorn) 실행 + 서비스클러스터 kubeconfig 주입 → 프론트 real 모드 전환 | ⬜ |

### 왜 이 방식인가
- **레지스트리 없음** → 컨테이너 이미지 빌드/푸시 불가 → 소스를 반입해 **프로세스로 직접 실행**.
- **관리망 격리** → git clone 불가 → 맥북 로컬 repo에서 `git archive` 떠서 scp 반입.
- **controller 노드 sudo 없음** → 시스템 패키지 설치 불가 → **nvm(Node) + pip --user(Python)** 로 사용자 홈에만 런타임 구성.
- **외부에서 노드 포트 직접 접근 불가** → 외부는 오직 `210.114.95.50:25443`(→ istio-ingressgateway)만 열림 → **Istio VirtualService로 노출**.

## 2. 환경 / 네트워크 전제

### 노드 구성 (Genestack, K8s v1.31.2)
- master1-3: control-plane (172.29.236.151-153) — **master3는 root, kubectl 사용**
- controller: worker (172.29.236.154) — **okes 사용자, 비root, sudo 없음** ← 프론트 프로세스 실행 위치
- 그 외 compute1/5/6, mlt 등 worker

### 접속 경로
```
맥북 ──SSH(-p 25222)──▶ okes@210.114.95.51 (controller 셸)
맥북 ──HTTPS(:25443)──▶ 210.114.95.50 ──NAT──▶ istio-ingressgateway(192.168.90.252:443)
```
- 맥북에서 서비스는 **오직 `210.114.95.50:25443`** 로만 접근 가능 (3000/8000/22/443 등은 필터링됨).
- `/etc/hosts` 에 `*.kcloud.cluster.local → 210.114.95.50` 매핑되어 있어야 함.
- 기존 OpenStack API도 동일 패턴: `nova-api.kcloud.cluster.local:25443` 등.

### Istio ingress 자원 (기존)
- `istio-ingressgateway` (LoadBalancer, EXTERNAL-IP 192.168.90.252, 443:30457)
- Gateway `istio-system/openstack-service-gateway` — selector `istio: ingressgateway`, 443 HTTPS(SIMPLE, cert `kcloud-cert-tls`), hosts에 `*.kcloud.cluster.local` OpenStack API 11종.
- 각 API는 `openstack` ns의 VirtualService(nova-vs 등)로 내부 Service에 라우팅.

## 4. 절차

### STEP 1 — controller 런타임 준비 (sudo 없이)

**Node.js (nvm):**
```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
# 셸 재시작 후
nvm install 20
node -v   # v20.20.2
npm -v    # 10.8.2
```

**Python pip (백엔드용, M3에서 사용 — venv 불가 우회):**
```bash
# python3-venv 미설치 + sudo 없음 → venv 대신 --user pip
python3 -m pip --version \
  || python3 -m ensurepip --user \
  || (curl -sS https://bootstrap.pypa.io/get-pip.py | python3 - --user)

# ~/.local/bin PATH 등록
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
export PATH="$HOME/.local/bin:$PATH"

# 백엔드 의존성 (M3에서 실제 사용)
python3 -m pip install --user fastapi "uvicorn[standard]" kubernetes httpx websockets
python3 -m uvicorn --version   # uvicorn 0.54.0
```

> 핵심: `venv`가 막혀도 `ensurepip --user` 또는 `get-pip.py --user`로 pip를 홈에 부트스트랩하고
> `pip install --user`로 설치하면 root 없이 해결된다.

---

### STEP 2 — 소스 반입 (맥북 → controller)

**맥북 로컬 repo에서 아카이브 생성** (`git archive`, node_modules/docs 제외):
```bash
cd <openkcloud repo>
# 프론트 (브랜치 전체)
git archive --format=tar.gz -o /tmp/front.tgz origin/feature/real-notebook-api
# 백엔드 (cmp-backend subtree, 매뉴얼 docs 제외하고 코드만)
git archive --format=tar.gz -o /tmp/back.tgz origin/feature/cmp-backend \
  cmp-backend/.gitignore cmp-backend/README.md cmp-backend/config.env.example \
  cmp-backend/main.py cmp-backend/deploy cmp-backend/pipelines
```

**scp 전송** (포트 옵션은 대문자 `-P`):
```bash
scp -P 25222 /tmp/front.tgz /tmp/back.tgz okes@210.114.95.51:~/mnt_notebook/
```

**controller에서 분리 해제** (프론트/백엔드 섞이지 않게 각각 폴더):
```bash
cd ~/mnt_notebook
mkdir -p front back
tar xzf front.tgz -C front    # ~/mnt_notebook/front/  (package.json 등)
tar xzf back.tgz  -C back     # ~/mnt_notebook/back/cmp-backend/
```

---

### STEP 3 — 프론트 빌드 & 실행 (controller)

**포트 선정** (기본 3000 대신 충돌 없는 고포트, 노드 IP에만 바인딩 → 최소 노출):
```bash
for p in 38080 39000 38443; do ss -ltn | grep -q ":$p " && echo "$p 사용중" || echo "$p 비어있음"; done
# → 38080 선택
```

**의존성 설치:**
```bash
cd ~/mnt_notebook/front
npm install
```

**tmux로 세션 분리 후 프로덕션 빌드·실행** (셸 닫아도 유지):
```bash
tmux new -s nb-front
# ── tmux 안 ──
cd ~/mnt_notebook/front
# NEXT_PUBLIC_ 변수는 빌드 시점에 코드에 박히므로 build/start 둘 다에 지정
NEXT_PUBLIC_KF_API=mock npm run build
NEXT_PUBLIC_KF_API=mock npm start -- -H 172.29.236.154 -p 38080
# 분리: Ctrl-b 뗀 뒤 d
```

> **왜 dev가 아니라 프로덕션 빌드인가:** `next dev`는 HMR 웹소켓(`/_next/webpack-hmr`)을
> 사용하는데, HTTP/2 ingress 뒤에서 이 wss 핸드셰이크가 502로 실패해 화면이 안 뜬다.
> `npm run build` + `npm start`는 HMR 소켓이 없어 이 문제가 원천 제거된다.

**노드 로컬 확인:**
```bash
tmux ls                                  # nb-front 살아있는지
curl -I http://172.29.236.154:38080/     # HTTP/1.1 200 OK
```

---

### STEP 4 — Istio ingress 연결 (master3)

**4-1. 사전 백업 & 현재 상태 확인:**
```bash
# Gateway 백업 (복구용)
kubectl -n istio-system get gateways.networking.istio.io openstack-service-gateway -o yaml \
  > ~/gw-openstack-service-gateway.bak.yaml

# 현재 hosts (패치 전 11개, notebook 없음 확인)
kubectl -n istio-system get gateways.networking.istio.io openstack-service-gateway \
  -o jsonpath='{range .spec.servers[0].hosts[*]}{@}{"\n"}{end}'

# controller 노드 IP 확인 (Endpoints 대상)
kubectl get nodes -o wide | grep -iE 'NAME|controller'   # INTERNAL-IP = 172.29.236.154
```

**4-2. Gateway에 notebook 호스트 추가** (기존 hosts 끝에 append — additive, 기존 무영향):
```bash
kubectl -n istio-system patch gateways.networking.istio.io openstack-service-gateway \
  --type=json \
  -p='[{"op":"add","path":"/spec/servers/0/hosts/-","value":"notebook.kcloud.cluster.local"}]'
```
확인 (총 12개):
```bash
kubectl -n istio-system get gateways.networking.istio.io openstack-service-gateway \
  -o jsonpath='{range .spec.servers[0].hosts[*]}{@}{"\n"}{end}'
```

**4-3. Service / Endpoints / VirtualService 생성** (새 ns `mnt-notebook`, 기존과 격리):
```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: mnt-notebook
---
# selector 없는 Service → 아래 수동 Endpoints로 매핑
apiVersion: v1
kind: Service
metadata:
  name: notebook-frontend
  namespace: mnt-notebook
spec:
  ports:
    - name: http
      port: 3000
      targetPort: 38080
      protocol: TCP
---
# controller 노드(프로세스 위치)로 직접 연결. port name은 Service와 동일("http")해야 매핑됨.
apiVersion: v1
kind: Endpoints
metadata:
  name: notebook-frontend        # Service 이름과 동일
  namespace: mnt-notebook
subsets:
  - addresses:
      - ip: 172.29.236.154       # controller INTERNAL-IP
    ports:
      - name: http
        port: 38080
        protocol: TCP
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: notebook-vs
  namespace: mnt-notebook
spec:
  gateways:
    - istio-system/openstack-service-gateway
  hosts:
    - notebook.kcloud.cluster.local
  http:
    - match:
        - uri:
            prefix: /
      route:
        - destination:
            host: notebook-frontend.mnt-notebook.svc.cluster.local
            port:
              number: 3000
EOF
```
확인:
```bash
kubectl -n mnt-notebook get svc,endpoints,vs
# endpoints 가 172.29.236.154:38080 을 가리키면 정상
```

> **포트 매핑 관계**
> | 계층 | 값 |
> |---|---|
> | 실제 프로세스 | `172.29.236.154:38080` |
> | Endpoints port | 38080 (name: http) |
> | Service port | 3000 → targetPort 38080 |
> | VirtualService dest | Service:3000 |
> | 외부 접속 | `:25443` |

## 5. 트러블슈팅 기록

| 증상 | 원인 | 해결 |
|---|---|---|
| `python3 -m venv` 실패 (ensurepip 없음) | python3-venv 미설치 + sudo 없음 | `ensurepip --user`/`get-pip.py --user` → `pip install --user` |
| pip/uvicorn "not on PATH" 경고 | `~/.local/bin` 미등록 | `.bashrc`에 PATH 추가 |
| 브라우저 502 `wss .../_next/webpack-hmr` + 화면 안 뜸 | `next dev` HMR 웹소켓이 HTTP/2 ingress 뒤에서 실패 | 프로덕션 빌드(`npm run build && npm start`)로 전환 |
| 셸 닫으면 프로세스 종료 | 포그라운드 실행 | tmux 세션(`nb-front`)에서 실행 후 detach |
| 기본 3000 포트 위험/충돌 우려 | 실배포 유사 노드 | 고포트(38080) + 노드 IP 바인딩(0.0.0.0 지양) |

### 참고: 웹소켓
M3에서 백엔드(cmp-backend)는 터미널/로그용 WebSocket을 사용한다. 그때는 ingress에서
웹소켓 업그레이드를 열어줘야 하며, 지금 프론트 목업 단계에서는 불필요하다.

## 6. 롤백 (원상복구)

```bash
# Service/Endpoints/VS 일괄 제거 (네임스페이스째)
kubectl delete ns mnt-notebook

# Gateway에서 추가한 notebook 호스트 제거 (12개면 마지막 index 11)
kubectl -n istio-system patch gateways.networking.istio.io openstack-service-gateway \
  --type=json -p='[{"op":"remove","path":"/spec/servers/0/hosts/11"}]'
# 또는 백업으로 복구
kubectl apply -f ~/gw-openstack-service-gateway.bak.yaml

# 프론트 프로세스 종료
tmux kill-session -t nb-front
# 또는
pkill -f "next .*38080"
```

기존 OpenStack API 트래픽에는 영향 없음(호스트 기반 라우팅 + 새 ns 격리).
