# 테넌시 · 권한 경계 정리 (IaaS / PaaS 서비스 클러스터 / AI 노트북)

작성: 2026-10-15 · 갱신: 2026-10-16 · 목적: 모듈별 권한 경계가 달라 "서비스 클러스터 공유 시 권한 분배"가 애매한 문제를 정리하고 방향을 결정한다.

## 0. 결론 요약 (2026-10-16)

- **운영 모델: 서비스 클러스터는 기본 "전용"(1 클러스터 : 1 프로젝트), 공유는 예외.** 프로젝트가 조직/과제/업무 경계이므로 전용이 자연스럽다. 공유가 설득력 있는 유일 케이스는 비싼 가속기(NPU/GPU) 노드 공동 활용 정도.
- **가시성은 `paas_project_cluster`(N:N) 매핑으로 처리(구현 완료).** 전용이면 프로젝트 1개만 매핑, 공유도 수용 가능하게 구조는 열어 둔다.
- **클러스터 내부 RBAC 격리(2단계)는 보류·과제화.** 공유가 예외라 지금은 불필요.
- **⚠️ 중대 전제 — 현재 kubeconfig 는 전원에게 cluster-admin 을 발급한다.** `MNT-PAAS/app/k8s_client.py:issue_client_cert` 가 CSR 을 `CN=admin, O=system:masters` 로 Magnum 에 서명시킨다 = 쿠버네티스 최고 권한. 전용 모델에선 "그 프로젝트 사용자가 자기 클러스터 전권"이라 문제없다. **그러나 공유하는 순간 격리가 전혀 안 된다** — 포털에서 네임스페이스를 아무리 제한해도 사용자가 kubeconfig 를 받아 kubectl 로 직접 접속하면 전체를 보고 조작할 수 있다. 따라서 **공유 클러스터에는 이 kubeconfig 발급을 허용하면 안 된다.** 공유가 필요해지면 RBAC 격리(아래 6-2)를 먼저 구현한 뒤에만 공유를 연다.

## 1. 기본 전제

사용자는 **자신이 속한(iam_project_member) 프로젝트의 자원만** 요청·조회·운영한다. 관리자는 전체.
그런데 "프로젝트"가 각 모듈에서 **무엇으로 실현되는지**가 달라서, 공유 클러스터에서 경계가 흐려진다.

## 2. 현재 3개 모듈의 권한 경계 (실제 구현 기준)

| 모듈 | 경계 단위 | 스코프 방식 (코드) | 격리 수준 |
|---|---|---|---|
| **IaaS** | OpenStack **프로젝트** | `iam_project_member` → 내 프로젝트만. OpenStack이 프로젝트 격리를 네이티브 강제 | 깔끔 |
| **PaaS 서비스 클러스터** | **클러스터(소유 프로젝트)** | Magnum 클러스터의 `project_id` 가 내 프로젝트 멤버십에 있으면 노출 (`cluster-scope-bar.tsx`: `myProjectIds.has(c.projectId)`) | 클러스터 단위만. **내부 네임스페이스/워크로드는 프로젝트별로 안 나뉨** |
| **AI 노트북 (Kubeflow)** | **네임스페이스(Kubeflow Profile)** | Profile 라벨 `openkcloud.io/project-id` = 프로젝트 **1:1**, 내 프로젝트 Profile만 | 네임스페이스 단위 격리 |

## 3. 문제: 서비스 클러스터를 여러 기관/프로젝트가 공유할 때

현재 PaaS 는 **"클러스터 1개 = 소유 프로젝트 1개"** 전제다. 공유하면 두 가지가 깨진다.

1. **소유권 충돌** — 클러스터가 프로젝트 A 소유이면 B 사용자는 볼 수 없다. 보이게 하려고 전원을 A에 넣으면 프로젝트 격리가 무너진다.
2. **내부 미분할** — PaaS 워크로드/서비스/스토리지 화면은 **클러스터 전체(또는 선택 네임스페이스)** 를 조회·조작한다. 공유하면 **B가 A의 워크로드를 모두 보고 건드릴 수 있다.** 클러스터 내부를 프로젝트별로 나누는 장치가 없다.

## 4. 이미 있는 "정답 방향" — 노트북의 프로젝트↔Profile 1:1

협의된 **"OpenStack 프로젝트 ↔ Kubeflow Profile 1:1"** 이 바로 공유 클러스터 다기관 문제의 표준 해법이다.
Kubeflow Profile = **네임스페이스 + RBAC + ResourceQuota** 이므로:

- 공유 클러스터 하나 위에 **프로젝트마다 네임스페이스(Profile)** 를 둔다.
- 사용자는 **자기 프로젝트의 네임스페이스만** 접근한다.

→ **"네임스페이스를 테넌트 경계로"** 하는 모델. 노트북은 이미 이 모델이고, **PaaS 일반 워크로드는 아직 클러스터-소유 모델**이라 둘이 어긋나 있다. 이것이 "정리가 안 되는" 근본 원인.

## 5. 결정해야 할 것 — 서비스 클러스터의 테넌트 경계

- **A. 네임스페이스 = 경계 (권장 · 노트북과 통일)**
  공유 클러스터 + 프로젝트↔네임스페이스 매핑. PaaS 워크로드/서비스/스토리지 조회·조작을 **그 매핑으로 스코프**(현재 클러스터 단위 → 네임스페이스 단위). 다기관 공유 가능, 격리 확보.
  - 필요한 일: ①프로젝트↔네임스페이스 매핑 저장소 ②목록/상세/쓰기 API에 네임스페이스 스코프 가드 ③사용자는 자기 네임스페이스만, 관리자는 전체.
- **B. 클러스터 = 경계 (현재 유지)**
  프로젝트/기관마다 전용 클러스터. 단순·확실하지만 **공유 불가**, 자원 낭비.
- **C. 혼합**
  일부는 전용(B), 일부는 공유(A: 네임스페이스 스코프).

노트북이 A를 따르므로 **A로 통일**하는 것이 일관적이다.

## 6-1. 채택 방향 (2026-10-16 최종)

**운영 모델을 "기본 전용(B), 공유는 예외"로 확정.** (0절 결론 참고) 5절의 A/B/C 중 상시 공유(A/C)는 채택하지 않는다 — 프로젝트가 조직/과제 경계이므로 전용이 자연스럽고, 공유는 가속기 공동 활용 같은 예외에 한함.

**구현한 것 — 가시성(공유 여부와 무관하게 유용)**
- **매핑 저장**: 포털 DB `paas_project_cluster`(프로젝트↔클러스터 N:N). 키 `project_id`(불변 UUID), 표시명은 조인. `namespace` NULL=전용(클러스터 전체), 값=공유(그 네임스페이스만 — 미래 격리용 데이터).
- **클러스터 가시성**: 전체 조회 후 사용자는 **내 프로젝트에 매핑된 클러스터만** 노출(소유 `project_id` → 매핑 `/my-cluster-ids` 기준으로 전환). 관리자는 전체. 전용이면 프로젝트 1개만 매핑하면 된다.
- **관리 화면**: 클러스터 상세 모달의 "접근 프로젝트" 섹션(관리자 전용)에서 부여/회수. `paas_project_cluster` CRUD.

**보류 — 클러스터 내부 RBAC 격리(2단계)**
- 공유가 예외라 **지금 구현하지 않는다.** `namespace` 칼럼·공유 입력은 데이터로만 받아 두고, 실제 격리 효력은 없다(가시성만 적용).
- **공유를 실제로 열려면 반드시 선행**해야 하는 것은 6-2(RBAC 격리)다. 그 전엔 공유 클러스터 kubeconfig 발급을 막아야 한다(0절 ⚠️).

**API (MNT-CORE)**
- `GET /clusters/{id}/access` — 접근 프로젝트 목록(관리 화면)
- `POST /clusters/{id}/access` (admin) — 부여 `{projectId, namespace?}`
- `DELETE /clusters/{id}/access?projectId=&namespace=` (admin) — 회수
- `GET /my-cluster-ids` — 내가 접근 가능한 클러스터 ID(사용자 가시성)

## 6-2. 공유 격리(미래 과제) — 공유가 필요해질 때만 착수

공유 클러스터를 안전하게 열려면 **포털 필터가 아니라 클러스터(kube-apiserver) 레벨에서 격리를 강제**해야 한다(사용자가 kubeconfig 로 직접 접속하므로). 후보:

- **(가) 프로젝트별 클라이언트 인증서** — `issue_client_cert` 의 `O=system:masters` 를 `O=<프로젝트 식별 group>` 으로 바꿔 발급 + 클러스터에 그 group → 네임스페이스 한정 RoleBinding. 포털만으로 가능, 외부 인프라 없음. 개인 단위 감사는 제한적(그룹 단위).
- **(나) Keycloak OIDC** — kube-apiserver 가 Keycloak 토큰을 직접 검증, 사용자별 신원·그룹으로 RBAC. 개인 단위 감사 best. 단 apiserver 설정·재기동 등 추가 인프라 필요.
- **(다) 네임스페이스별 ServiceAccount** — 간단하나 사람≠SA 라 **감사(누가 했는지 ns 단위까지만)·토큰 만료/회수 관리가 애매** → 사람 접속용으로 비권장.

권장 순서: 공유가 생기면 **(가)** 부터(기존 CSR 서명 흐름 재사용). 개인 감사가 요구되면 **(나)** 로 확장. 멀티 서비스 클러스터(외주 설계 요청 건)와 함께 설계.

## 6-3. 남은 미결 질문 (공유를 열 때 다시 볼 것)

1. **매핑 관리 위치**: 프로젝트↔네임스페이스 매핑을 포털 DB vs 클러스터 라벨(`openkcloud.io/project-id`, 노트북 방식) 중 어디서?
2. **네임스페이스 생성 주체**: 네임스페이스(+RBAC+Quota)를 누가 언제? (노트북은 워크스페이스 신청→Profile 생성. PaaS 도 동일 신청 흐름?)
3. **멀티 서비스 클러스터**(외주 설계)와의 조합: 클러스터 선택 × 네임스페이스 스코프 두 축.
4. **격리 방식 확정**: 6-2의 (가)/(나)/(다).
