## 0. ⚠️ 컨트롤러에서 직접 변경한 것 (소스 드리프트 기록)

**백엔드/프론트 소스 코드는 수정하지 않았다.** 컨트롤러(`~/mnt_notebook/`)의 소스는 git(`feature/cmp-backend`, `feature/real-notebook-api`)과 동일하다. 바꾼 것은 아래 3가지뿐:

1. **`~/mnt_notebook/back/cmp-backend/config.env` 신규 생성** (소스 아님, 환경파일 — git에 없음). 내용은 3장 참조.
2. **파이썬 의존성 교체** (환경, 소스 아님): 잘못 설치된 더미 패키지 `websocket`(0.2.1) 제거 + `websocket-client` 재설치. (kubernetes 클라이언트가 `websocket.ABNF`를 요구 → 더미가 덮어써서 ImportError였음)
   ```bash
   python3 -m pip uninstall -y websocket websocket-client
   python3 -m pip install --user 'websocket-client>=1.6'
   ```
3. **프론트 빌드타임 env** (소스 아님, 빌드 인자): `NEXT_PUBLIC_KF_API`, `NEXT_PUBLIC_MSW_ENABLED`. 4장 참조.

> 즉 **코드 수정 필요 시에는** 로컬 repo에서 고쳐 커밋 → `git archive` → scp 재반입해야 하며, 현재까지는 그런 변경이 없다.

## 1. 목표 / 아키텍처

- 프론트(`real-notebook-api`)의 `NEXT_PUBLIC_KF_API`를 실제 백엔드로 향하게 하여, 포털에서 노트북 CRUD·IDE 연결.
- 백엔드(`cmp-backend`, FastAPI)는 **서비스 클러스터 kubeconfig**로 Kubeflow Notebook/Profile CRD를 조작.
- 배포는 M1과 동일: **컨트롤러 프로세스 + Istio ingress**.

## 3. config.env (컨트롤러 신규 생성)

`~/mnt_notebook/back/cmp-backend/config.env`:
```bash
# 백엔드 외부 주소 = 프론트와 같은 오리진(단일 오리진 리버스 프록시) — IDE URL도 이 호스트로 발급
PUBLIC_BASE_URL=https://notebook.kcloud.cluster.local:25443
CORS_ORIGINS=https://notebook.kcloud.cluster.local:25443
# 노트북 생성 대상 워크스페이스 = Profile okc
DEFAULT_NAMESPACE=okc
DEFAULT_NOTEBOOK_IMAGE=kubeflownotebookswg/jupyter-scipy:v1.9.2
# 이 클러스터는 NVIDIA GPU Operator 아님 → RuntimeClass 강제 안 함(비움)
GPU_RUNTIME_CLASS=
# 로컬 WSL 전용 우회값 — 실클러스터라 비움
DEV_PIN_NODE=
POD_HTTP_PROXY=
# 백엔드가 붙을 서비스 클러스터 kubeconfig
KUBECONFIG=/home/okes/mnt_notebook/kubeconfig-k8s-furiosa-rngd/config
```

> `PUBLIC_BASE_URL`은 처음에 `notebook-api...`로 뒀다가, **단일 오리진 설계**(kf.ts가 https면 같은 origin으로 호출)에 맞춰 `notebook...`(프론트와 동일)으로 변경.

## 4. 백엔드 실행 + ingress 노출

### 4-1. 실행 (컨트롤러, tmux `nb-back`, 포트 38001)
```bash
cd ~/mnt_notebook/back/cmp-backend
export KUBECONFIG=/home/okes/mnt_notebook/kubeconfig-k8s-furiosa-rngd/config
python3 -m uvicorn main:app --host 172.29.236.154 --port 38001 --env-file config.env
```
로컬 헬스체크: `curl -I http://172.29.236.154:38001/docs` → 200.

### 4-2. ingress (master3) — Gateway 호스트 추가 + Service/Endpoints/VS
```bash
# notebook-api 호스트 추가(직접 백엔드 테스트용, 선택)
kubectl -n istio-system patch gateways.networking.istio.io openstack-service-gateway \
  --type=json -p='[{"op":"add","path":"/spec/servers/0/hosts/-","value":"notebook-api.kcloud.cluster.local"}]'
```
백엔드 Service/Endpoints/VS: `deploy-notebook-m3-backend.yaml` (port 8000 → targetPort 38001, 노드 172.29.236.154).
맥북 확인: `curl -k -I https://notebook-api.kcloud.cluster.local:25443/docs` → HTTP/2 200.

### 4-3. 단일 오리진 경로 라우팅 (핵심)
프론트 호출은 전부 `${KF_BASE}/api/v1/*`, IDE 프록시는 `/notebook/{ns}/...`. 쿠키 인증(okc_session, HttpOnly)이라 **크로스 오리진이면 쿠키 미전송→인증 깨짐** → **한 호스트로 합치고 경로 분기**:
`notebook-vs`를 아래로 갱신 (master3):
```yaml
http:
  - match:
      - uri: { prefix: /api/ }
      - uri: { prefix: /notebook/ }   # 뒤 슬래시 — 프론트 /notebooks 와 충돌 방지
    route: [ { destination: { host: notebook-api.mnt-notebook.svc.cluster.local, port: { number: 8000 } } } ]
  - match:
      - uri: { prefix: / }
    route: [ { destination: { host: notebook-frontend.mnt-notebook.svc.cluster.local, port: { number: 3000 } } } ]
```

## 5. 프론트 real 모드 재빌드 (컨트롤러)

빌드타임 env 2개 동시 지정:
```bash
cd ~/mnt_notebook/front
NEXT_PUBLIC_KF_API=auto:8000 NEXT_PUBLIC_MSW_ENABLED=false npm run build
NEXT_PUBLIC_KF_API=auto:8000 NEXT_PUBLIC_MSW_ENABLED=false npm start -- -H 172.29.236.154 -p 38080
```
- `NEXT_PUBLIC_KF_API=auto:8000` → https 접속 시 `window.location.origin`으로 호출(kf.ts) = 같은 오리진 → `/api/v1/*`가 4-3에 의해 백엔드로 감.
- `NEXT_PUBLIC_MSW_ENABLED=false` → 목업 서비스워커 완전 비활성.

> `NEXT_PUBLIC_MSW_ENABLED`는 `NEXT_PUBLIC_KF_API`와 **독립적**이다(msw-provider.tsx). real 모드여도 이 값을 false로 안 주면 MSW가 SW 등록을 시도하고, self-signed 인증서라 SW 등록이 차단되어 콘솔 에러가 난다.

## 6. 관찰된 증상과 해석

| 요청 | 결과 | 해석 |
|---|---|---|
| `/api/dashboard/summary·activities·alerts` | 404 | **MSW 목업 전용** 엔드포인트(cmp-backend에 없음). 포털 대시보드 위젯용 — 노트북 기능과 무관, 무해 |
| `/api/v1/profiles` | 500 | **라우팅은 정상**(백엔드 도달). 백엔드 내부 예외 |

### 500의 근본 원인 = 서비스 클러스터 소멸
`/api/v1/profiles` 트레이스백:
```
HTTPSConnectionPool(host='192.168.90.225', port=6443): [Errno 113] No route to host  /apis/kubeflow.org/v1/profiles
```
→ 백엔드가 furiosa 서비스 클러스터 API(`192.168.90.225:6443`)에 도달 불가. **원인: 공유 furiosa 클러스터가 Horizon에서 사라짐(삭제/소멸)** → 우리가 올린 Kubeflow·okc 프로파일·연결 전부 소멸. (M2에서 경고한 "공유 클러스터 소유자 재생성 시 소멸" 리스크가 현실화)

## 7. 결론 / 다음 단계

- **M3 파이프라인 자체는 정상 작동**: 백엔드 기동 → ingress 노출 → 단일오리진 라우팅 → 프론트 real 전환까지 검증됨. `/api/v1/profiles`가 백엔드에 도달해 500을 낸 것이 곧 **연동 경로가 살아있다는 증거**.
- **차단 요인은 서비스 클러스터 부재** 하나. → **우리 전용 서비스 클러스터 재생성** 필요(공유 의존 탈피).
- 전용 클러스터 생성 시 **calico 이미지 egress 리셋 → CAPI 재생성 루프** 문제를 넘겨야 함:
  1. 재시도 babysitting (calico-node 파드 반복 delete로 pull 관철) — furiosa도 이렇게 3회 만에 떴음
  2. 레지스트리 미러를 Magnum 템플릿에 주입(근본책) — mgmt 노드 containerd 미러 존재 여부 확인 필요
- 재생성 후: kubeconfig 경로만 `config.env`에 갱신 → 백엔드 재기동 → 프론트는 그대로 → 노트북 생성 재검증.
- 이후: IDE 연결 **WebSocket**(HTTP/2 게이트웨이 뒤 wss 502 가능성) 대응, NPU 활성화 + 백엔드 NPU 적응.

## 8. (2026-09-29) 전용 클러스터 재구축 & 노트북 실제 생성

공유 클러스터 소멸 후 **우리 전용 `k8s-okc-nb`** 를 Horizon에서 재생성(템플릿 `ct-k8s-1.36.2-rngd-nodash-nogpu`, 1+1).

### 8-1. 클러스터 생성 — 이번엔 성공
- 지난번(`k8s-mnt-nb`)은 calico 이미지 egress 리셋 → CAPI 재생성 루프로 사망했으나, 이번엔 **calico-node가 RESTARTS 2회 만에 스스로 Running** → 노드 Ready. (전송 리셋은 일시적, 재시도로 뚫림이 재확인됨. babysitting 루프는 불필요했음)
- kubeconfig: `~/mnt_notebook/kubeconfig-k8s-okc-nb`, API `192.168.90.205:6443`. controller에서 `kubectl` 도달 OK.

### 8-2. Kubeflow + Profile 재설치
M2와 동일(istio CRD + notebook/profile controller v1.10) + Profile `okc`.
**쿼터**: Profile을 owner만으로 만들면 배정량 0 → 노트북 생성 시 "몫 초과". `resourceQuotaSpec.hard` 부여로 해결(소스 아님):
```bash
kubectl apply -f - <<'EOF'
apiVersion: kubeflow.org/v1
kind: Profile
metadata: { name: okc }
spec:
  owner: { kind: User, name: okc@openkcloud.local }
  resourceQuotaSpec:
    hard: { cpu: "16", memory: 32Gi, requests.storage: 500Gi }
EOF
```

### 8-3. StorageClass 문제 (중요, 소스 아님)
노트북 PVC가 Bound됐으나 Pod가 `FailedAttachVolume` — **Cinder 볼륨이 error 상태**. 원인:
- 서비스 클러스터 기본 SC가 **`rbd1`**(볼륨타입 `rbd1`, **백엔드 호스트 미지정** → Cinder가 볼륨 생성 못 하고 error)
- 정상은 **`rbd`** SC(볼륨타입 `RBD` → `cinder-volume-worker@RBD#RBD` 백엔드, 노드 디스크들이 이걸로 정상 동작)

백엔드 코드는 PVC에 `storageClassName`을 **지정하지 않음**(클러스터 기본 SC 사용) → **기본 SC만 교체하면 소스 수정 없이 해결**:
```bash
kubectl annotate sc rbd1 storageclass.kubernetes.io/is-default-class-
kubectl annotate sc rbd  storageclass.kubernetes.io/is-default-class=true
```
재생성 후 PVC가 `rbd`로 Bound, attach 정상. (근본적으론 rngd 템플릿의 rbd1 볼륨타입 백엔드 매핑을 ETRI가 정리해야 함)

### 8-4. 이미지 pull 불안정 (인프라)
노트북 이미지(`kubeflownotebookswg/codeserver-python:v1.9.2`, docker.io, 수 GB)가 `ImagePullBackOff` — calico와 동일한 **전송 리셋**. 추정 원인: **오버레이 테넌트망 MTU/MSS 불일치**(작은 요청 OK, 대용량 blob 리셋) + **egress 방화벽/NAT**. 관리(베어메탈) 클러스터가 멀쩡한 것과 대조. **근본책 = 레지스트리 미러**(관리망 내부에서 pull), 임시 = 재시도(containerd가 캐시 누적).

### 8-5. IDE(code-server) 인증·프록시 체인 검증 — 통과 ✅
브라우저에서 연결 시 재로그인창이 떠서 CLI로 전 구간 검증:
```bash
# 1) 로그인 → set-cookie: okc_session=... (정상 발급)
curl -k -i -X POST https://notebook.kcloud.cluster.local:25443/api/v1/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"Okc!2026#admin"}'
# 2) 그 쿠키로 IDE 프록시
curl -k -i -b "okc_session=<값>" https://notebook.kcloud.cluster.local:25443/notebook/okc/my-traning-lab/
#   → HTTP/2 302  location: ./?folder=/home/jovyan   ← code-server 정상 폴더열기(=인증통과+노트북도달)
```
- 결론: **로그인 쿠키 발급 → 프록시 인증 통과 → code-server 도달까지 정상**. 302 `./?folder=`는 로그인 리다이렉트가 아니라 code-server의 정상 동작.
- 브라우저 재로그인창은 **로그인 시점 okc_session 미발급(그때 백엔드/라우팅 준비 전, 실패가 조용히 무시됨)** 때문. 백엔드가 살아있는 지금 **브라우저 재로그인**하면 발급됨. (세션 비밀키는 `~/.cmp-secret`에 영속 → 재시작해도 무효화 안 됨)

### 8-6. 남은 것
- 브라우저 재로그인 후 IDE(iframe) 정상 표시 확인 (경미)
- 이미지 pull 안정화 = **레지스트리 미러** (인프라)
- **NPU 활성화**: worker에 Furiosa PCI(1ed2) 존재하나 device plugin 미설치. 드라이버+플러그인+런타임(벤더) 필요. cmp-backend는 NVIDIA 전제라 NPU 노트북은 코드 적응 필요 → CPU 노트북 먼저 완성.
- IDE **WebSocket**(code-server 터미널 등) HTTP/2 게이트웨이 뒤 동작 확인.
